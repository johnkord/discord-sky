# Discord Sky maintenance atlas

Start with the user's observable problem. The [runtime map](../runtime_architecture.md) describes how a turn flows; the [decision register](../decisions/README.md) says which behavior is intentional. For environment-specific access, start with the [ops runbook](../../.github/skills/discord-sky-ops/SKILL.md). Do not put real room content, guild IDs, tokens, or private inventories in this atlas.

## Inspect one turn

The [turn inspector](../../scripts/inspect_turn.py) runs locally on an owner-private snapshot. It has no network client, uses no credentials, and does not open transcripts, profile Secrets, or personal-note files. Access is controlled by the snapshot's filesystem permissions, not by a Discord role. Use the original JSON; do not convert snowflakes to floating point or round them in a spreadsheet.

Point it at the directory containing `telemetry/recall-YYYY-MM-DD.jsonl` and/or `world-autonomy/world-autonomy.json`. Include only relevant telemetry days. For an independent native write result, include `world-autonomy/<guild-id>/steward/operations.json` for the originating guild. There is no need to export the rest of the PVC. Do not upload these files to a public issue or CI.

```bash
python3 scripts/inspect_turn.py /path/to/private-snapshot --message 5001
python3 scripts/inspect_turn.py /path/to/private-snapshot --request 00000000-0000-4000-8000-000000000001 --json
```

Use `--message` for a trigger or a recorded output message; `--run` and `--request` take a UUID. The view joins only exact identifiers. It separates audience decisions and projected reply parents from provider dispatch and acknowledged messages, identifies confirmed partial chunks and cross-channel sends, and labels independent Steward observations separately from Sky's stored copy. It cannot tell whether someone enjoyed a line, why Robotnik privately declined, whether a post still exists today, or how much an unmetered cancellation cost. A request missing from the primary Sky journal is not a reason to search unrelated guilds. Exit codes: `0` match, `1` no match in supplied evidence, `2` bad input or unreadable schema. `--json` is also private metadata.

## Authority and evidence

For full-run host speech or final images, the inspector lists the attempt separately from its receipt. `no_receipt` can mean a crash before or after dispatch; `unknown` means the acknowledgement was inconclusive. Neither is proof of delivery or silence. Inspect Discord read-only. A `journal_unavailable` terminal summary can coexist with a confirmed post and a run still marked `running` on disk. The [pinned-child delivery fixture](../../tests/DiscordSky.Tests/StewardMcpSupervisorIntegrationTests.cs) covers preflight failure, partial delivery, an unknown first send, and completion failure after a confirmed send.

- Sky owns the gateway and routing. Steward's separate child and private profile delimit administrative authority for each exact bound guild. Do not narrow that catalog to tune style, or extend those permissions to unbound guilds. Disabled guilds remain excluded before active behavior. Notes and Empire lore are not isolated by a Steward binding.
- Live overrides come from the [Deployment](../../k8s/discord-sky/deployment.yaml), in order: primary Secret, public ConfigMap, private autonomy bindings, private runtime bindings. These override app settings. Query only the named effective fields you need; never dump Secrets or all environment variables.
- For [investigations](../../.github/skills/discord-sky-investigation/SKILL.md), capture pod start/image and UTC window first. Join trigger, episode/run, provider call and Discord IDs. Use Discord for what was visible, journals for effects, telemetry for admission and costs, and the owner for quality. Where sources disagree, record an unknown.
- Stdout rotates. Treat it and the PVC as private. Enabled transcript, telemetry and reaction sinks prune whole expired UTC day files at startup and hourly. Those retentions do not imply deletion of operation journals or backups.

## Validate and release

1. Use a local synthetic fixture for the smallest risk first: `dotnet test tests/DiscordSky.Tests/DiscordSky.Tests.csproj -c Release --filter 'FullyQualifiedName~WorldAutonomyLedgerTests'` is one example. Real Discord changes and paid provider calls require a distinct, justified test; they are not normal release checks.
2. On Linux with .NET 10, Python 3 and system SQLite, check out the [Steward pin](../../scripts/steward-ref) in a clean sibling checkout. Run `bash scripts/validate-release.sh`; set `STEWARD_TEST_ROOT` for another path or `RESULTS_DIRECTORY` for a retained TRX. A missing sibling, failed audit feed or missing required integration is not a passing release.
3. Follow the [deployment runbook](../../k8s/discord-sky/README.md). Normally main deploys after validation. For an explicitly requested pre-commit rollout, stage the exact validated tree, check for unstaged source, use `git write-tree` in place of `git rev-parse 'HEAD^{tree}'`, and use the same pinned sibling. Tag format: `tree-<40-char-sky-tree>-s<7-char-steward-sha>`. Verify that the subsequent commit has that exact tree.
4. Capture current image/digest, revision, private binding versions and guard state without printing credentials or message text. Use the hardened script with `--include-steward --preserve-steward-profiles`. Verify one Ready pod, digest, `/livez`, `/healthz`, child counts/catalog and auth/model access. No destructive probes or synthetic chat posts in production.
5. Stop on a mismatching pin/digest, unhealthy child, missing binding, failed gate or unexplained budget reset. The deploy script restores prior config and revision on rollout failure; for an observed regression, redeploy the known-good source/config pair with the same private bindings. Never roll the PVC back to make a test green.

When behavior or data boundaries change, update the decision with the alternative rejected and evidence that would reverse it. Keep live settings in the runbook, deployments in git/Actions, and owner-private observations out of both.
